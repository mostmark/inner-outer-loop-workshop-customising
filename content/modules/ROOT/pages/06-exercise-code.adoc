= Tutorial 6: Add the code for an exercise
include::partial$_attributes.adoc[]

The last piece of ACME's chapter is in the code repository: the application participants build,
a devfile command for the chapter's *IDE Task* tab, a solution for participants who skip ahead,
and the cleanup. After this tutorial, participants can follow the chapter from start to finish.

[cols="1,3"]
|===
| Goal | The ACME exercise in your code fork, and a participant who builds and runs ACME Hello
following the new chapter
| You need | xref:05-add-an-operator.adoc[Tutorial 5] completed
| Time | about 30 minutes
|===

== How the code repository works

Every participant's workspace clones your code fork to `/projects/workshop`, so participants see
everything in it. Keep it to what they need.

[cols="2,3"]
|===
| Path | Contains

| `labs/` | the applications participants work on
| `.tasks/` | the scripts behind the devfile commands; they all source `.tasks/workshop-env.sh`,
which knows the participant's user, projects and this repository's URL (`CODE_REPO_URL`)
| `.tasks/solutions/` | the finished state of the exercises, for participants who skip ahead
| `devfile.yaml` | the workspace: its containers and the devfile commands (*Terminal → Run
Task...*)
|===

[IMPORTANT]
====
The lab guide refers to devfile commands by their *label*. Never change an existing label;
adding commands is fine.
====

== Step 3: Add the devfile command

In `devfile.yaml`, add the command after `inner-loop---deploy-coolstore`, the fast-forward of
Part 1:

[source,yaml]
----
  - id: acme---build-with-shipwright
    exec:
      label: ACME - Build with Shipwright
      component: workshop-tools
      workingDir: /projects/workshop/.tasks
      commandLine: '. ./workshop-env.sh && ./acme_build_shipwright.sh'
----

The label must be exactly the one the chapter names.

== Step 5: Extend the cleanup

The devfile command "OpenShift - Cleanup" (`.tasks/openshift_cleanup.sh`) resets a participant's
workshop, and must remove everything a participant can create. In `.tasks/openshift_cleanup.sh`,
after `+workshop_clean_project "${STAGING_PROJECT}"+`, add:

[source,bash]
----

# ACME: the Shipwright exercise in acme-<user>. Shipwright runs each build as a Tekton TaskRun,
# which stays when its BuildRun is deleted; it keeps the build pod.
info "Deleting the ACME Hello resources in acme-${WORKSHOP_USER}"
oc delete buildruns.shipwright.io,taskruns.tekton.dev,builds.shipwright.io,deployment,service,route,imagestream \
  --all -n "acme-${WORKSHOP_USER}" --ignore-not-found > /dev/null 2>&1
----

Also mention it in the comment at the top of the file:

[source,bash]
----
#   - deletes the participant's Argo CD Applications <svc>-<user> (without cascading),
#   - deletes the ACME Hello build and deployment in acme-<user>.
----

== Step 6: Commit and push

----

== Troubleshooting

[cols="2,3"]
|===
| Problem | Solution

| *Run Task* doesn't list "ACME - Build with Shipwright" | The workspace started before the
change: restart it from the Dev Spaces dashboard.
| `labs/acme-hello` is missing in the workspace | Run `git pull` in `/projects/workshop`.
| The BuildRun fails while fetching the source | The build clones your code fork from its URL
(`CODE_REPO_URL`), so the fork must be readable without credentials, and the code pushed to
`main`.
| `oc apply` of the Build fails with `no matches for kind "Build"`, or the Build shows
`REGISTERED False` | Builds for Red Hat OpenShift is not installed or not ready yet (tutorial 5):
`oc get csv -n openshift-builds`, `oc get clusterbuildstrategies`.
| `oc logs ...-pod` says the container is waiting to start | The build has not started yet. Wait
a few seconds and try again.
| The route answers `503` | The new route needs a few seconds; reload the page.
|===

== What's next

ACME now has its own version of the workshop: its look, a new chapter, the operator that chapter
needs, a project per participant and the exercise code, all installed through GitOps and
removed again by `cleanup.sh`.

To take over improvements of the original workshop later, merge its `main` into your forks, one
repository at a time, for example:

[source,bash,subs="attributes+"]
----
cd "$WORKDIR/{GITOPS_REPO}"
git remote add upstream {GITOPS_REPO_URL}.git   # once
git fetch upstream
git merge upstream/main
----

Conflicts appear only where you edited the same lines as the original. That's why the tutorials
put most of ACME's changes into files of their own.
