= Using your own Git server and registry
include::partial$_attributes.adoc[]

The tutorials use GitHub for your forks and quay.io for your images. You can use another Git
server (for example GitLab, Gitea or GitHub Enterprise) and another container registry instead.
This page lists what changes. If you use GitHub and quay.io, you can skip it.

The tutorials were tested end to end this way: with the three repositories on a self-hosted
GitLab, and the lab guide image in a quay.io organisation.

[IMPORTANT]
====
The cluster must be able to *read* your repositories and images *without credentials*: the
repositories and image repositories must be public, or at least readable without logging in from
the cluster's network. Private repositories and registries are not supported yet.
====

== Who reads your repositories and images

These components on the cluster fetch from your Git server and registry:

[cols="2,2,3"]
|===
| Component | Reads | Configured in

| Argo CD (`openshift-gitops`) | the gitops repository | `bootstrap.sh --repo`, and the
repository URLs in the gitops repository (tutorial 1 lists them)
| DevWorkspace operator | the code repository's `devfile.yaml`, as a raw file | `devspaces.devfileURL`
in `charts/workshop-users/values.yaml`
| Every participant's workspace | the code repository (clone) | `devspaces.repositoryURL` in
`charts/workshop-users/values.yaml`
| Job `maven-warmup` | the code repository (clone) | `nexus.warmup.repositoryURL` in
`charts/workshop-platform/values.yaml`
| Lab guide Deployment | the lab guide image | `labGuide.image` in
`charts/lab-guide/values.yaml`
| Every participant's workspace, Job `maven-warmup` | the tooling image, if you build your own |
the code repository's `devfile.yaml`, `nexus.warmup.image` in
`charts/workshop-platform/values.yaml`
|===

== Differences to GitHub

[cols="1,2,2"]
|===
| What | GitHub | Your own Git server

| Copying the repositories
| the *Fork* button
| create three empty repositories, then copy each one:

`git clone --bare <original URL>` +
`git -C <name>.git push --mirror <your URL>`

Some servers can also import a repository by URL, for example GitLab's *Import project*.

| Raw file URL of `devfile.yaml` (for `devspaces.devfileURL`)
| `\https://raw.githubusercontent.com/<org>/<repo>/main/devfile.yaml`
| depends on the server, for example:

GitLab: `\https://<host>/<group>/<repo>/-/raw/main/devfile.yaml` +
Gitea: `\https://<host>/<org>/<repo>/raw/branch/main/devfile.yaml`

Open the URL in a private browser window: it must show the plain file without a login.

| Preview of the lab guide on the web
| the lab guide repository's GitHub Pages workflow (`.github/workflows/gh-pages.yml`)
| not covered; preview locally (tutorial 1) or on the cluster
|===

== Tutorial 1, steps 2 and 3 on your own Git server

The commands of tutorial 1 use GitHub's URL formats. On your own server, use these instead. Set the
address of your group or organisation once, without a trailing slash:

[source,bash]
----
export GIT_BASE=https://gitlab.example.com/acme
----

*Step 2*, clone your copies:

[source,bash,subs="attributes+"]
----
mkdir -p "$WORKDIR" && cd "$WORKDIR"
for repo in {GITOPS_REPO} {GUIDE_REPO} {CODE_REPO}; do
  git clone "$GIT_BASE/$repo.git"
done
----

*Step 3*, point the copies to each other. These commands are for GitLab; the first `sed` expression
writes GitLab's raw-file URL of `devfile.yaml`. For another server, change `/-/raw/main/` to that
server's format (see the table above).

[tabs]
====
macOS::
+
--
[source,bash,subs="attributes+"]
----
cd "$WORKDIR"
for repo in {GITOPS_REPO} {GUIDE_REPO} {CODE_REPO}; do
  (cd "$repo" && git grep -l -e 'github.com/{GITHUB_UPSTREAM}/' -e 'githubusercontent.com/{GITHUB_UPSTREAM}/' \
      -e 'quay.io/{GITHUB_UPSTREAM}/inner-outer-loop-lab' -- ':!docs' \
    | xargs sed -i '' -E \
        -e "s|https://raw.githubusercontent.com/{GITHUB_UPSTREAM}/([a-z-]+)/main/|$GIT_BASE/\1/-/raw/main/|g" \
        -e "s|https://github.com/{GITHUB_UPSTREAM}/|$GIT_BASE/|g" \
        -e "s|github.com/{GITHUB_UPSTREAM}/|${GIT_BASE#https://}/|g" \
        -e "s|quay.io/{GITHUB_UPSTREAM}/inner-outer-loop-lab|quay.io/$QUAY_USER/inner-outer-loop-lab|g")
done
----
--
Linux::
+
--
[source,bash,subs="attributes+"]
----
cd "$WORKDIR"
for repo in {GITOPS_REPO} {GUIDE_REPO} {CODE_REPO}; do
  (cd "$repo" && git grep -l -e 'github.com/{GITHUB_UPSTREAM}/' -e 'githubusercontent.com/{GITHUB_UPSTREAM}/' \
      -e 'quay.io/{GITHUB_UPSTREAM}/inner-outer-loop-lab' -- ':!docs' \
    | xargs sed -i -E \
        -e "s|https://raw.githubusercontent.com/{GITHUB_UPSTREAM}/([a-z-]+)/main/|$GIT_BASE/\1/-/raw/main/|g" \
        -e "s|https://github.com/{GITHUB_UPSTREAM}/|$GIT_BASE/|g" \
        -e "s|github.com/{GITHUB_UPSTREAM}/|${GIT_BASE#https://}/|g" \
        -e "s|quay.io/{GITHUB_UPSTREAM}/inner-outer-loop-lab|quay.io/$QUAY_USER/inner-outer-loop-lab|g")
done
----
--
====

Check the result as in tutorial 1. Besides the tooling image and the link to these tutorials,
`git grep -n {GITHUB_UPSTREAM} -- ':!docs'` also shows the GitHub Pages preview link in the lab
guide's `README.adoc`, which doesn't apply to your server. Make sure `devspaces.devfileURL` in `charts/workshop-users/values.yaml` opens the
plain `devfile.yaml` in a private browser window.

In the other tutorials, read `github.com/$GITHUB_USER` as your server's address (`$GIT_BASE`).

== Your own container registry

The build scripts push to quay.io:

* `build-push-container.sh` (lab guide repository) pushes
  `quay.io/$QUAY_USER/inner-outer-loop-lab:latest`;
* `tools/build-push.sh` (gitops repository) pushes `quay.io/$QUAY_USER/workshop-tools:latest`.

To use another registry, change the `IMAGE=` line of the script in your fork, for example:

[source,bash]
----
IMAGE="registry.example.com/acme/inner-outer-loop-lab:latest"
----

Both scripts stop with `QUAY_USER is not set` before they reach the `IMAGE=` line. Set
`QUAY_USER` anyway (any value, for example your user name), or remove that check in your fork.

Log in with `podman login <registry>` before you run the script, and make the image repository
readable without credentials. Then use the same image name in the chart values (see the table
above).

[NOTE]
====
The cluster's internal image registry can hold the images too, but it takes extra setup: a
project of its own (not one the workshop creates, because `cleanup.sh` deletes those), a route
for pushing, and permission for the workshop's projects to pull. These tutorials use a registry
outside the cluster.
====
